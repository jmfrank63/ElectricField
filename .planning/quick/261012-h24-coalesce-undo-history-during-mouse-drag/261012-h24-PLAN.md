<objective>
Coalesce the undo history a charge drag produces. Today every mouse-move frame of a canvas drag goes through `editor::moveCharge` (ui.cpp:133-138), whose `recordHistory()` pushes a full pre-state snapshot per position change — one drag floods `Tab::undo` (capped at 100, so long drags also evict all older history), and one Ctrl+Z rewinds a single mouse frame instead of one user action.

Mechanism decision (evaluated per the item): **(a) explicit begin/commit drag transaction in the editor — CHOSEN.** The open-transaction state lives on `Tab` next to `undo`/`redo`, the editor stays pure (no ImGui/SDL types), the undo stack keeps plain whole-snapshot semantics, and the transaction is unit-testable without a GUI. (b) suppress-flag on moveCharge + record-on-release was rejected: the release-time record still needs the pre-drag state, so it degrades into the same snapshot with its responsibility scattered into the GUI. (c) coalescing adjacent same-index moves inside the undo stack was rejected: it cannot distinguish a drag from arrow-key steps or two separate consecutive drags of the same charge, and turns `undo()` into a heuristic.

Behaviour locked for this plan (decide-and-test points resolved):
- One drag (press -> move -> release) that moved the charge records exactly ONE entry — the pre-drag state — so one undo restores it.
- Release with no net movement records nothing: both "never moved" and "dragged away and back to the exact start position" (exact X and Y equality, matching moveCharge's existing no-op comparison).
- A drag transaction SURVIVES a mid-drag computation: the entry is recorded on mouse release for the whole drag, not per computation boundary (auto-recalc users hit this on every drag longer than 0.35 s).
- The dragged charge removed mid-drag (Delete key, ui.cpp:150): commitDrag bounds-checks and discards; the removal's own entry stands.
- An arrow-key nudge pressed during an active drag of the same charge folds into that drag's single entry (accepted edge; without an open transaction arrows stay one-entry-per-press).

Purpose: undo granularity becomes user-action granular during drags and the 100-entry cap stops being consumed by single gestures.

Output: the transaction API + Tab state, drawCanvas wiring, extended smoke assertions, five doctest cases. No doc changes: docs/api.md documents the command API where per-move semantics are unchanged, and README does not document mouse-undo behaviour.
</objective>
