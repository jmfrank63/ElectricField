# Phase 261012-h24 Plan 01: Coalesce undo history during mouse drag Summary

A canvas charge drag now produces exactly ONE undo entry — the pre-drag snapshot — via a pure editor begin/commit drag transaction, so one Ctrl+Z restores the pre-drag position and the 100-entry history cap is no longer consumed by a single gesture; proven by five new doctest cases, extended headless-smoke assertions, and the unchanged 10-editor.efscript pin.

## What Was Built

- **Tab state (src/app/workspace.hpp):** `int dragIndex = -1` (the dragged charge during an open drag, -1 = none — the same sentinel style as `selected` / `pendingRecalcAt`) and `HistoryEntry dragPre` (the pre-drag snapshot, valid only while `dragIndex >= 0`). No new includes.
- **Transaction API (src/app/editor.hpp/.cpp):** `beginDrag` captures `{t.field, t.params.method}` by value and no-ops while computing (D-02: no NEW drags), on an out-of-range index, or when a transaction is already open (never overwrites the snapshot). `commitDrag` moves the snapshot out and closes the transaction first (exception-safe ordering), then discards on an out-of-range index (removed mid-drag), discards on exact X/Y equality with the pre-drag position (no net movement / returned to the start — the same comparison as moveCharge's no-op), and otherwise pushes ONE entry with recordHistory's cap-erase-oldest rule and the redo clear. It touches none of stale / dirty / pendingRecalcAt / scene / computed. `dragActive` is a one-line inline in the header.
- **Silent moveCharge (src/app/editor.cpp:57):** only the `recordHistory(t)` call is gated (`dragIndex < 0 || dragIndex != (int)index`); mutation, scene sync, stale, dirty, and `pendingRecalcAt = -2` stay unconditional, so realtime-draw semantics are byte-identical (verified by diff inspection).
- **drawCanvas wiring (src/gui/ui.cpp:132-148):** the drag branch opens the transaction on the first drag frame (keyed on `dragActive`); the commit fires after the drag if/else on `!ImGui::IsMouseDown(0) && dragActive(t)` — the release frame itself, which also covers releasing off-canvas or after an interruption. Click-select, double-click-add, arrow, Delete, and Esc blocks untouched; `ui.canvasDrag` contract unchanged.
- **Smoke oracle (src/gui/app.cpp:737-748):** right after the existing drag-moved assertion — undo stack empty when the drag began, so counts are exact: fail unless `undo.size() == 1` (catches both over- and under-recording, message includes the actual count); `editor::undo` must restore X exactly 0.0 (snapshot restore, no arithmetic); `editor::redo` must return X ≥ 0.4 (same threshold style as the drag assertion). The following double-click-add targets a far-away empty spot, so the round-trip does not disturb it.
- **Five doctest cases (tests/test_editor.cpp):** one-entry coalescing with undo/redo round-trip (and the mid-drag second-begin no-op), no-net-movement records nothing (both never-moved and moved-back-to-exact-start), discrete moves + stepSelected stay one-entry-per-call and never open a transaction, a transaction spans a real mid-drag computation (moveCharge refused while computing, dragActive survives, commits once at (0,0) origin restore), and the removed-mid-drag discard (no crash, no entry).

### Smoke flake diagnosis (both outcomes recorded per the dispatch constraint)

The battery's two consecutive failures were both the documented pre-existing check `clicking the origin charge did not select it` — never any of the new assertions. Verified pre-existing by baseline comparison: the parent commit (cde371c) was built in a throwaway worktree and reproduced the identical failure (its Debug smoke run failed on the same check; subsequently 5/5 ReleaseFast and 6/6 Debug passes on the baseline binary). My plan's assertions are direct `editor::` calls on the workspace (no injected input, no pacing dependency), so they add no new flake surface. No fix applied: the flake predates this plan and touches an out-of-scope file region (scope boundary); the orchestrator's dispatch constraints already track it.
